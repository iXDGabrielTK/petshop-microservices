# DEBT-ARCH-002 — Runbook PR 3: E4 (concorrência e anti-deadlock)

> Runbook executável e autocontido. Contexto arquitetural e justificativas: [README.md](./README.md).

## Contexto e pré-requisitos

- Módulo: `apps/inv-service` (Spring Boot 3.4, Java 21, Testcontainers/PostgreSQL). Pré-requisito: PR 2 (E2–E3) mergeado: `VendaService` e `VendaEventHandler` consomem `inv.inventory.api.EstoqueCommandService`, cuja implementação (`EstoqueService`) ordena os itens por `produtoId` crescente e executa um `UPDATE` atômico por item (ADR-0002, `docs/adr/0002-atomic-sql-inventory-and-hybrid-locking.md`).
- Ordem global de row locks em `produtos` (`produtoId ASC`): impede ciclo de espera, logo `40P01` entre comandos de estoque. `INSERT`s com FK pegam só `FOR KEY SHARE`, que não conflita com o `FOR NO KEY UPDATE` dos `UPDATE`s de saldo.
- Nesta etapa o único código de produção alterado é o `@Retryable`/`@Recover` de `VendaService.iniciarVenda`; o resto são testes.

## Invariantes
- **Q3** — **Operações em lote nos três comandos.** A implementação ordena os itens internamente por `produtoId` crescente (ordenação estável), **independente da ordem do chamador**, e executa **um `UPDATE` atômico por item**. **Proibido** usar `UPDATE ... FROM (VALUES ...)`: o PostgreSQL não garante a ordem de aquisição dos locks em um único statement com join.
  - **Impacto:** Ordem global de locks → sem ciclo de espera entre carrinhos (F5). As 3 queries atômicas de `ProdutoRepository` (ADR-0002) ficam **inalteradas**. Teste `CarrinhosInvertidosDeadlockIT` + controle negativo (E4).
- **Q8** — **Resiliência:** incluir `PessimisticLockingFailureException` no `@Retryable` de `iniciarVenda`. O `VendaEventHandler` **não** ganha retry de método para lock pessimista: o container RabbitMQ (`max-attempts=3`, backoff exponencial) já cobre falhas transitórias e encaminha para a DLQ ao esgotar. A ordenação (Q3) é a mitigação **estrutural primária**; o retry é rede de segurança.
  - **Impacto:** `@Recover` passa a receber `ConcurrencyFailureException` (superclasse comum de `OptimisticLockingFailureException` e `PessimisticLockingFailureException`), com a **mesma mensagem** ao usuário. O retry (outer) envolve o `@Transactional` (inner): cada tentativa é uma transação nova (`@EnableRetry` tem precedência sobre o advisor transacional). Teste `IniciarVendaRetryIT` (E4).
- **F5** (🟠 Alta) — **Risco de deadlock `40P01` em carrinhos multi-item.** Reserva, baixa e estorno iteram os itens na ordem do request / da coleção, que é arbitrária. Dois carrinhos `[A, B]` e `[B, A]` simultâneos formam um ciclo de espera nos row locks de `produtos`, que duram até o fim da transação. O PostgreSQL aborta uma delas após o `deadlock_timeout`, e o operador do PDV vê um erro 500.
  - **Evidência:** [VendaService.java#L59-L63](../../../apps/inv-service/src/main/java/inv/checkout/usecase/VendaService.java#L59-L63), [#L125-L127](../../../apps/inv-service/src/main/java/inv/checkout/usecase/VendaService.java#L125-L127), [VendaEventHandler.java#L63-L65](../../../apps/inv-service/src/main/java/inv/checkout/infrastructure/messaging/VendaEventHandler.java#L63-L65)
  - **Impacto:** Ordenação determinística por `produtoId` crescente dentro de `EstoqueService` nos 3 comandos em lote (Q3), formalizada no adendo à ADR-0002 (**E2/E3**). Validado na **E4** com `CarrinhosInvertidosDeadlockIT` + controle negativo.
- **F8** (🟡 Média) — **Teste de integração cruzando módulos.** `EstoqueConcorrenciaIntegrationTest` fica em `inv.inventory` e importa classes de `checkout` e `ProdutoRepository`. Passa no ArchUnit só por causa de `ImportOption.DoNotIncludeTests`.
  - **Evidência:** [EstoqueConcorrenciaIntegrationTest.java#L1-L7](../../../apps/inv-service/src/test/java/inv/inventory/EstoqueConcorrenciaIntegrationTest.java#L1-L7), [ArquiteturaTest.java#L22](../../../apps/inv-service/src/test/java/inv/architect/ArquiteturaTest.java#L22)
  - **Impacto:** Mantido fora da análise. Na **E4**, testes ponta a ponta que cruzam módulos são movidos para o pacote `inv.it`, preservando a integridade de suas asserções.
- **ADR-0002** — a hierarquia de locks (`vendas` → `produtos` em ordem crescente) e as três queries atômicas de `ProdutoRepository` não mudam. `EstoqueConcorrenciaIntegrationTest` é o gate absoluto de validação concorrente.

### Referência: retry de `iniciarVenda` (Q8)

```java
@Retryable(
        retryFor = { OptimisticLockingFailureException.class, PessimisticLockingFailureException.class },   // Q8
        backoff = @Backoff(delay = 150, maxDelay = 500, random = true)
)
@Transactional
public Venda iniciarVenda(VendaRequest pedido) { /* corpo inalterado */ }

@SuppressWarnings("unused")
@Recover
public Venda recuperarFalhaDeConcorrencia(ConcurrencyFailureException e, VendaRequest pedido) {   // cobre otimista + pessimista
    log.warn("⚠️ Limite de retries atingido por contenção de lock no estoque. Venda abortada.");
    throw new BusinessException(
            "Alta concorrência nos itens selecionados. O estoque foi atualizado por outro caixa. Por favor, tente finalizar novamente.");
}
```

## Passos

### E4 — Validação de concorrência pesada + resiliência (Q8)

- **Pré-requisitos/Artefatos:** E3 concluída.
  - Incluir `PessimisticLockingFailureException.class` no `@Retryable` de `VendaService.iniciarVenda` e alterar o `@Recover` para `ConcurrencyFailureException` (trecho em "Referência: retry de iniciarVenda" acima).
  - Mover [`EstoqueConcorrenciaIntegrationTest.java`](../../../apps/inv-service/src/test/java/inv/inventory/EstoqueConcorrenciaIntegrationTest.java) para `inv.it` (F8), preservando a integridade de suas asserções.
- **Testes:**
  - `EstoqueConcorrenciaIntegrationTest` (existente: 50 threads × 5 unidades, `CountDownLatch`): **inalterado e verde** (gate absoluto da ADR-0002).
  - `inv/it/EstoqueMultiItemConcorrenciaIT`: 50 threads com carrinhos alternando `[A, B]` e `[B, A]`; `A` com 5 unidades e `B` com 1.000.
    - Exatamente 5 sucessos; 45 falhas com `"Estoque insuficiente para o produto: <A>"`.
    - Estado final: `A.disponivel = 0`, `A.reservado = 5`, `B.reservado = 5` (prova de rollback atômico do lote).
    - Movimentações `RESERVA` = 10; **0** exceções com SQLState `40P01`.
  - `inv/it/CarrinhosInvertidosDeadlockIT` (prova da ordenação `Q3`/`F5` + controle negativo):

    ```java
    @Test
    @DisplayName("Q3/F5 — 20 pares de carrinhos invertidos [A,B] vs [B,A] na CyclicBarrier executam com 0 deadlocks")
    void carrinhosInvertidosSimultaneosNaoCausamDeadlock() throws Exception {
        int pares = 20; // 40 threads
        CyclicBarrier barreira = new CyclicBarrier(pares * 2);
        AtomicInteger sucessos = new AtomicInteger();
        Queue<Throwable> erros = new ConcurrentLinkedQueue<>();

        try (ExecutorService pool = Executors.newFixedThreadPool(pares * 2)) {
            for (int i = 0; i < pares; i++) {
                pool.submit(() -> executarNaBarreira(barreira, List.of(item(idA, "1.000"), item(idB, "1.000")), sucessos, erros));
                pool.submit(() -> executarNaBarreira(barreira, List.of(item(idB, "1.000"), item(idA, "1.000")), sucessos, erros));
            }
            pool.shutdown();
            assertThat(pool.awaitTermination(30, TimeUnit.SECONDS)).isTrue();
        }

        assertThat(erros).isEmpty();
        assertThat(sucessos.get()).isEqualTo(40);
        assertThat(produtoRepository.findById(idA).orElseThrow().getEstoqueReservado()).isEqualByComparingTo("40.000");
        assertThat(produtoRepository.findById(idB).orElseThrow().getEstoqueReservado()).isEqualByComparingTo("40.000");
    }
    ```
    - **Controle negativo** no mesmo IT: duas `TransactionTemplate`s chamam diretamente `produtoRepository.reservarEstoqueAtomo` em ordem **invertida**, intercaladas por `CountDownLatch` (T1 trava A, T2 trava B, T1 pede B, T2 pede A), com `deadlock_timeout=100ms` no container. Deve ocorrer **exatamente 1** `PessimisticLockingFailureException` (`SQLState 40P01`), provando que o ambiente detecta o deadlock caso a ordenação seja removida.
  - `inv/it/HandlerExpiracaoMesmaVendaIT`: pagamento e expiração da **mesma** venda disparados simultaneamente (`CyclicBarrier`), 30 repetições: sempre um único vencedor (`CONCLUIDA` com baixa, ou `CANCELADA` com estorno), **0** deadlocks e saldos coerentes.
  - `IniciarVendaRetryIT` (`@SpringBootTest` + `@MockitoBean EstoqueCommandService`): 1ª chamada lança `CannotAcquireLockException`, 2ª tem sucesso → `iniciarVenda` retorna a venda, o mock é chamado 2× e a venda da tentativa 1 foi revertida; esgotadas as 3 tentativas, `@Recover` lança `BusinessException` com a mensagem amigável.
- **Critérios de aceite:** todos os testes acima verdes em **3 execuções consecutivas** no CI (anti-flaky). p95 de `iniciarVenda` no IT multi-item ≤ o baseline da E0 + 10%.
- **Commits sugeridos:** `test(it): concorrência multi-item e anti-deadlock com controle negativo` → `feat(checkout): retry de iniciarVenda para lock pessimista`.
- **Rollback:** reverter o retry (aditivo). Os testes permanecem.
