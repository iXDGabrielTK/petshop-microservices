## 1. Contexto & Invariantes

- **Pré-condições Técnicas e Fronteira Afetada:**
  - A tabela `pagamentos` possui constraint única `uk_pagamento_uuid` em `uuid_referencia` e coluna `valor_esperado NUMERIC(10, 2)`.
  - [`GlobalExceptionHandler`](../../../apps/common-lib/src/main/java/common/exception/GlobalExceptionHandler.java#L44) intercepta `Exception.class` (retornando HTTP 500), exigindo `@ExceptionHandler(ConflictException.class)` explícito em `common-lib` para responder HTTP 409 `ProblemDetail` sem criar handler temporário em [`PagamentoController`](../../../apps/inv-service/src/main/java/inv/checkout/infrastructure/web/controller/PagamentoController.java).
  - Preserva-se a transação única de `criarIntencaoPagamento`, mantendo o lock da venda até commit ou rollback. Na regra `R15` (`ArquiteturaTest`), `criarIntencaoPagamento` apenas lê `venda.getStatus()` e `venda.getId()` (não muta `Venda`), adquirindo `findByIdWithLock` para serializar com conclusão/expiração/cancelamento da venda.

- **Q3 — Semântica HTTP (`404` / `409` / `400`) e Normalização Decimal Sem Arredondamento:**
  - **Semântica de Status:** `404` (`ResourceNotFoundException`) quando `vendaId` não existir; `409` (`ConflictException`) quando `venda.getStatus().aceitaPagamento()` for `false` **ou** quando `uuidReferencia` já existir com divergência em `vendaId`, `metodo` ou `valor` (`compareTo != 0`).
  - **Rejeitar, Nunca Arredondar:** A coluna `NUMERIC(10,2)` arredondaria silenciosamente `10.005` para `10.01`, causando falso `409` no retry idêntico. Em [`CriarIntencaoPagamentoRequest`](../../../apps/inv-service/src/main/java/inv/checkout/infrastructure/web/dto/CriarIntencaoPagamentoRequest.java), manter `@NotNull`, `@Positive` e adicionar `@Digits(integer = 8, fraction = 2)`. Como `@Digits` para `BigDecimal` avalia a escala literal recebida do Jackson (`10.000` tem `scale = 3`), o construtor compacto normaliza `valor` não nulo com `valor.stripTrailingZeros()` (e `setScale(0)` se escala negativa, ex.: `100` → `1E+2`), aceitando `10.000` e `100` e rejeitando `10.005` (`400`).
  - **Defesa em Profundidade no Service:** No início de `criarIntencaoPagamento`, rejeitar com `BusinessException` (400) quando `valor == null`, `valor.signum() <= 0`, `valor.compareTo(new BigDecimal("99999999.99")) > 0` ou `valor.stripTrailingZeros().scale() > 2`. Alinhar com clientes externos (PDV) para não enviarem valores com mais de 2 casas decimais.

- **F3 / Q3 — Protocolo em 6 Etapas de `PagamentoService.criarIntencaoPagamento`:**
  1. **Consulta rápida:** `findByUuidReferencia(uuidReferencia)`. Se presente, aplicar comparação compartilhada (`vendaId`, `metodo`, `valorEsperado.compareTo(valor) == 0`): coincidente retorna ID (`200`), inclusive se a venda já estiver concluída/cancelada; divergente lança `ConflictException` (`409`).
  2. **Lock pessimista na venda:** `vendaRepository.findByIdWithLock(vendaId)`. Se ausente, lançar `ResourceNotFoundException` (`404`), preservando a hierarquia de locks do Checkout.
  3. **Reconsulta pós-lock (antes do status da venda):** executar novamente `findByUuidReferencia(uuidReferencia)`. Se outra transação inseriu durante a espera do lock, aplicar a mesma comparação compartilhada (retornando `200` ou lançando `ConflictException`), preservando retries legítimos mesmo que a venda tenha mudado para `CONCLUIDA`/`CANCELADA` na espera.
  4. **Validação do status:** se `!venda.getStatus().aceitaPagamento()`, lançar `ConflictException` (`409`) sem inserir pagamento.
  5. **Inserção atômica com fonte única do domínio:** instanciar `new Pagamento(venda, metodo, valor, uuidReferencia)`, chamar `processar()` se `metodo.isExigeProcessamento()` for `true` e **ler `status`, `valorRecebido`, `excedente` e `contabilizado` da instância** (resultado esperado: `PROCESSANDO` ou `PENDENTE`, `0`, `false`, `false`; `nsu_transacao` e `data_hora_pagamento` nulos) para repassar ao `INSERT ... ON CONFLICT (uuid_referencia) DO NOTHING RETURNING id` via `@Query(nativeQuery = true)` **sem `@Modifying`** retornando `Optional<Long>` (enums persistidos via `name()`, padrão de `LancamentoFinanceiroRepository`). Se houver ID retornado, devolvê-lo.
  6. **Leitura de fallback em conflito:** se o `Optional<Long>` vier vazio, consultar `findByUuidReferencia(uuidReferencia)` e aplicar a mesma comparação compartilhada (`200` se igual; `ConflictException` `409` revertendo a transação se divergente), sem atualizar nem sobrescrever o registro existente.

## 2. Referência de Contratos (Published Language & DDL)

### Exceção HTTP 409 (`common-lib`) e Validação DTO (`CriarIntencaoPagamentoRequest`)

```java
// common.exception.ConflictException
@ResponseStatus(HttpStatus.CONFLICT)
public class ConflictException extends RuntimeException {
    public ConflictException(String message) { super(message); }
    public ConflictException(String message, Throwable cause) { super(message, cause); }
}

// GlobalExceptionHandler — @ExceptionHandler(ConflictException.class)
// Retorna ResponseEntity<ProblemDetail> HTTP 409 (title: "Conflito de Estado", type: "https://petshop.com/errors/conflict")
```

```java
// inv.checkout.infrastructure.web.dto.CriarIntencaoPagamentoRequest
public record CriarIntencaoPagamentoRequest(
        @NotNull(message = "O UUID de referência é obrigatório") UUID uuidReferencia,
        @NotNull(message = "Método de pagamento é obrigatório") MetodoPagamento metodo,
        @NotNull(message = "Valor é obrigatório")
        @Positive(message = "Valor deve ser maior que zero")
        @Digits(integer = 8, fraction = 2, message = "Valor deve ter no máximo 8 dígitos inteiros e 2 casas decimais")
        BigDecimal valor
) {
    public CriarIntencaoPagamentoRequest {
        if (valor != null) {
            BigDecimal normalizado = valor.stripTrailingZeros();
            valor = normalizado.scale() < 0 ? normalizado.setScale(0) : normalizado;
        }
    }
}
```

### Query Nativa Idempotente (`PagamentoRepository`)

```java
@Query(value = """
    INSERT INTO pagamentos (
        uuid_referencia, venda_id, metodo, status,
        valor_esperado, valor_recebido, excedente, contabilizado
    )
    VALUES (
        :uuidReferencia, :vendaId, :metodo, :status,
        :valorEsperado, :valorRecebido, :excedente, :contabilizado
    )
    ON CONFLICT (uuid_referencia) DO NOTHING
    RETURNING id
    """, nativeQuery = true)
Optional<Long> inserirIntencaoIdempotente(
        @Param("uuidReferencia") UUID uuidReferencia,
        @Param("vendaId") Long vendaId,
        @Param("metodo") String metodo,
        @Param("status") String status,
        @Param("valorEsperado") BigDecimal valorEsperado,
        @Param("valorRecebido") BigDecimal valorRecebido,
        @Param("excedente") boolean excedente,
        @Param("contabilizado") boolean contabilizado
);
```

### Critérios de Teste (Comportamento Esperado)

- **Cenário 1 — `404`, `409` por status incompatível e divergência por campo (`PagamentoServiceTest`):**
  - *Condição:* Venda inexistente; venda em `ABERTA`, `CONCLUIDA` ou `CANCELADA`; UUID existente com divergência individual em `vendaId`, `metodo` ou `valor`.
  - *Ação/Gatilho:* Chamar `criarIntencaoPagamento` em cada cenário.
  - *Asserção/Resultado Esperado:* Lança `ResourceNotFoundException` (`404`) quando venda não existe; `ConflictException` (`409`) para status incompatível sem chamar `inserirIntencaoIdempotente`; `ConflictException` (`409`) nas 3 divergências individuais; `10.0` vs `10.00` no mesmo pedido retorna ID existente (`200`).
- **Cenário 2 — Validação de escala decimal sem arredondamento (`PagamentoControllerTest`, `PagamentoServiceTest`):**
  - *Condição:* Entradas `10.005`, `10.000` (escala 3), `10.00`, `100`, `null`, `0`, `-1.00`, `100000000.00`.
  - *Ação/Gatilho:* Submeter ao DTO via `MockMvc` e diretamente ao `PagamentoService`.
  - *Asserção/Resultado Esperado:* `10.005` falha com `400` (`@Digits`) e `BusinessException`; `10.000`, `10.00` e `100` são aceitos sem arredondamento; no service, `null`, `<= 0`, `> 99999999.99` ou `scale > 2` lançam `BusinessException`; retry idêntico nunca gera `409`.
- **Cenário 3 — Retry após conclusão/cancelamento e reconsulta pós-lock (`PagamentoServiceTest` / `*IT`):**
  - *Condição:* Pagamento já existente enquanto venda foi concluída/cancelada, ou criado por transação concorrente durante a espera pelo lock.
  - *Ação/Gatilho:* Executar retry na etapa 1 e na etapa 3 (pós-lock).
  - *Asserção/Resultado Esperado:* Pedido igual retorna o ID existente (`200`); pedido divergente lança `ConflictException` (`409`).
- **Cenário 4 — Equivalência JPA vs nativo, `RETURNING id` e concorrência no PostgreSQL (`*IT`):**
  - *Condição:* Métodos com processamento (`CARTAO_CREDITO`) e sem processamento (`PIX`), e transações concorrentes sincronizadas com `CountDownLatch`/`CyclicBarrier` na mesma venda e em vendas diferentes.
  - *Ação/Gatilho:* Exercitar `inserirIntencaoIdempotente` (1ª inserção vs conflito `Optional.empty()`) e `criarIntencaoPagamento` concorrente no PostgreSQL Testcontainers.
  - *Asserção/Resultado Esperado:* Linha nativa idêntica ao JPA (`status`, `valor_recebido = 0`, `excedente = false`, `contabilizado = false`); na mesma venda, pedidos iguais com o mesmo UUID retornam o mesmo ID e persistem uma única linha; divergências em método ou valor retornam `409`. Entre vendas diferentes, o mesmo UUID é sempre divergente por `vendaId`: sincronizar ambas as transações após a reconsulta da etapa 3 e antes do INSERT para forçar o conflito, comprovando um vencedor e o fallback da etapa 6 com `409` no perdedor, uma única linha e nenhum dado sobrescrito. Cobrir separadamente em teste unitário o retorno de ID para payload igual no fallback, sem atribuir esse resultado à colisão entre vendas distintas.
